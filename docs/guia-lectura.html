Tecnologías del proyecto (y qué significan las siglas)

Cada herramienta, qué es (con la sigla explicada) y para qué se usa acá.

El diagrama de cómo se comunica todo

El usuario usa el navegador (el frontend: lo que se ve). El backend (el servidor: Apache + PHP) recibe el pedido, le pregunta a la base de datos (MySQL) y devuelve el HTML ya armado.

Las tecnologías, una por una

  • PHP (Hypertext Preprocessor): el lenguaje del backend. Corre en el servidor y arma el HTML que se manda al navegador.
  • MySQL: el motor de base de datos (BD) donde se guardan productos, categorías y usuarios.
  • PDO (PHP Data Objects): la "puerta" de PHP para hablar con MySQL. Se usa siempre con prepared statements (consultas preparadas) para evitar inyección SQL.
  • SQL (Structured Query Language): el idioma para pedirle y guardarle datos a la base (SELECT, INSERT, UPDATE, DELETE).
  • Apache: el servidor web que recibe las peticiones HTTP (HyperText Transfer Protocol) y ejecuta PHP.
  • Docker: empaqueta todo el entorno (PHP, MySQL, phpMyAdmin) en contenedores, para levantarlo con un comando y que a todos les funcione igual.
  • phpMyAdmin: un panel web para mirar y editar la base a mano, sin instalar nada.
  • HTML (HyperText Markup Language): la estructura de las páginas, lo que arman las vistas.
  • CSS (Cascading Style Sheets / hojas de estilo en cascada): el aspecto visual (colores, tamaños, posiciones).

El CSS: tres archivos y el orden en que se cargan

Todo el estilo entra por tres hojas de CSS, enlazadas en el encabezado de las páginas — el archivo real es app/Views/layouts/header.php — y se cargan en este orden, que es justamente lo que hace que todo funcione:

  1. Bootstrap 5 (framework de CSS) — public/assets/css/bootstrap.min.css, servido localmente (sin CDN, sin depender de internet). Aporta la base ya hecha: botones, tarjetas, alertas y la grilla (las clases que vas a ver en las vistas son btn, card, alert y row).
  2. Las fuentes — public/assets/fonts/fuentes.css, que define las tipografías (también locales, sin internet).
  3. El tema propio — public/assets/css/estilo.css. Va último a propósito: como en CSS el que se carga después gana, acá se "pisa" el look de Bootstrap y se define lo que Bootstrap no trae — los colores de la marca (con variables CSS), la barra superior, el menú, las tarjetas del tablero y los gráficos.
El truco del orden

Bootstrap pone los cimientos del estilo y estilo.css los personaliza; por eso el tema propio se enlaza al final. Además lleva un ?v=… con la fecha del archivo (mirá header.php): obliga al navegador a volver a bajar el CSS cuando cambia, en vez de mostrar una versión vieja guardada en caché.

¿Y el JavaScript? El sitio no usa

Puede sorprender, pero la aplicación no tiene JavaScript: no hay ningún archivo .js propio y tampoco se carga el JS de Bootstrap (solo su CSS). Todo lo que ves lo arma el servidor en PHP y lo viste el CSS:

  • Los gráficos del tablero son CSS puro (las barras con anchos; el pastel con conic-gradient).
  • El menú, los formularios y los avisos son HTML + CSS; la validación y la lógica corren en el backend.
  • Cada pantalla es una página completa que devuelve el servidor: no hay carga dinámica por JavaScript.

Es una decisión del proyecto: así es más simple, funciona aunque el navegador no ejecute JavaScript, y no hace falta ningún paso de compilación (build). El único JavaScript del repositorio está dentro de estas guías (docs/*.html), para las pestañas y los botones de copiar — no es parte del sitio.

¿Qué "APIs" se usan?

Una API (Application Programming Interface / interfaz de programación) es un conjunto de funciones que una herramienta ofrece para que otro código la use. Acá no se consumen APIs externas por internet; las que se usan son las que trae PHP:

  • La API de PDO para hablar con MySQL (preparar y ejecutar consultas).
  • La API de contraseñas de PHP: password_hash() y password_verify(), para guardar y comparar contraseñas sin verlas en texto.
  • La API de sesiones ($_SESSION) para recordar quién inició sesión entre páginas.

1. Mapa de archivos

Qué es cada archivo, a qué capa pertenece y si exige sesión iniciada.

El proyecto usa un MVC (Modelo-Vista-Controlador) hecho a mano, sin framework. En palabras simples: el backend (el código PHP del servidor) recibe el pedido, busca los datos en la base de datos, y arma el frontend (el HTML que ve el navegador).

La cara visible

  • public/index.php — el front controller: la ÚNICA puerta de entrada. Toda petición pasa por acá.
  • public/assets/ — estilos, Bootstrap y fuentes (lo visual que descarga el navegador).

El servidor (backend, carpeta app/)

  • app/Core/ — el motor: autoloader, helpers, conexión a la base, router y controlador base.
  • app/Controllers/ — reciben el pedido y deciden qué hacer (Producto, Categoria, Auth, Usuario).
  • app/Models/ — hablan con la base de datos (las consultas viven acá).
  • app/Middleware/ — los guardias: Auth (exige sesión) y Admin (exige rol admin).
  • app/Views/ — las plantillas que arman el HTML. Son "la cara", pero las genera el servidor.

La base de datos y la configuración

  • database/schema.sql — crea las tablas y los datos de prueba.
  • routes/web.php — la tabla de rutas: qué URL va a qué controlador, y si es privada.
  • config/config.php — de dónde salen las credenciales de la base (vive fuera de public/).

2. Cómo viaja una petición

Del navegador a Apache, de Apache a PHP, de PHP a MySQL, y el HTML de vuelta.

  1. El navegador pide una dirección, por ejemplo /index.php/productos.
  2. Apache sirve public/index.php (la raíz web es public/).
  3. El front controller arranca la sesión, carga el autoloader y los helpers, crea el Router y le pasa las rutas de routes/web.php.
  4. El Router busca la ruta que coincide con la dirección. Si es privada, primero corre el guardia Auth; si no hay sesión, manda al login.
  5. El Router crea el controlador y llama a su método (ej. ProductoController::index).
  6. El controlador le pide los datos al modelo, que consulta la base de datos con una consulta preparada.
  7. El controlador elige una vista, que arma el HTML. Eso es lo que vuelve al navegador.

Resumen: frontend (navegador) → backend (PHP) → base de datos → backend arma el frontend → navegador.

3. Un caso completo de punta a punta

Dar de alta un producto, siguiendo el recorrido real por los archivos.

  1. GET /productos/crear → el Router llama a ProductoController::crear(), que muestra la vista productos/crear.php (los campos están en _campos.php, compartidos con editar).
  2. Completás el formulario y apretás "Guardar". El formulario manda POST /productos.
  3. El Router llama a ProductoController::guardar(). Junta los datos del formulario y llama a Producto::validar().
  4. Si hay errores, vuelve a mostrar el formulario con los mensajes y lo ya escrito. Si está todo bien, llama a Producto::crear(), que hace el INSERT con una consulta preparada.
  5. Guarda un aviso ("Producto creado") en la sesión y redirige a /productos.
  6. Esa nueva petición muestra el listado; el aviso aparece una sola vez y se borra.

4. Patrones compartidos

Las dos estructuras que se repiten en varias páginas. Viven acá para no quedar duplicadas en cada archivo.

Una página, dos modos: GET muestra, POST procesa

Cada formulario tiene dos momentos: GET muestra el formulario vacío (o cargado), y POST procesa lo que mandaste. En el MVC eso son dos métodos distintos del controlador (ej. crear() muestra, guardar() procesa), conectados por el Router.

La validación de producto, compartida por crear y editar

Crear y editar comparten los mismos campos (_campos.php) y la misma validación (Producto::validar()): el nombre no puede estar vacío, y precio y stock deben ser números mayores o iguales a cero. Una sola definición, usada por las dos acciones.

Buscar y filtrar sin abrir la puerta a una inyección

Cómo index.php arma las condiciones del WHERE en PHP y deja que los valores viajen aparte — y por qué eso no es lo mismo que "armar la consulta a mano".

El método Producto::filtro() decide EN PHP qué condiciones entran al WHERE, pero lo que vos escribiste NUNCA se pega dentro del texto del SQL: viaja aparte, como parámetro de una consulta preparada. Por eso no se puede "inyectar" SQL: el valor siempre se trata como dato, nunca como código.

Avisos que se muestran una sola vez

Por qué el "Producto creado" viaja en la sesión y no en la dirección, y qué hace que no reaparezca al recargar.

Los avisos ("Producto creado", "Usuario eliminado") viajan en $_SESSION['mensaje']. El layout los muestra y los borra en el acto, así no reaparecen al recargar. Van en la sesión y no en la dirección para que la URL quede limpia.

Un gráfico de barras sin ninguna librería

Cómo una consulta agrupada se convierte en el ancho de un div, y por qué el proyecto no necesita descargar nada para dibujarlo.

El tablero tiene dos gráficos y ninguna librería ni JavaScript:

  • Barras (valor por categoría): una consulta agrupada devuelve el valor de cada categoría, y PHP convierte ese número en el ancho de un div.
  • Pastel/dona (unidades por categoría): PHP calcula el porcentaje de cada categoría y arma un conic-gradient de CSS. El agujero del centro es otro círculo encima.

Los dos respetan el filtro activo: si filtrás por una categoría, los gráficos se recalculan.

5. Glosario de PHP

Lo que se repite en todo el proyecto, explicado una sola vez y con ejemplos tomados de este mismo código.

Las superglobales: $_POST, $_GET, $_SERVER

$_POST trae lo que se envía por un formulario; $_GET, lo que viaja en la dirección (ej. ?buscar=cable); $_SERVER, datos del servidor (lo usa base_path() para que los enlaces funcionen en cualquier carpeta).

Los operadores ?? y ?:

$_POST['x'] ?? '' dice "si no existe, usá vacío" (evita avisos de PHP). $a ?: $b dice "si $a es falso/vacío, usá $b". Se ven por todo el código para poner valores por defecto en una línea.

Funciones de texto: trim(), htmlspecialchars(), number_format()

trim() saca espacios de los bordes; htmlspecialchars() (envuelta en el helper e()) escapa el texto para que el navegador no interprete HTML metido por un usuario (anti-XSS); number_format() da formato a los precios.

require, require_once y el orden de inclusión

El front controller usa require para cargar el autoloader y los helpers una sola vez. Las clases NO se incluyen a mano: el autoloader (app/Core/autoload.php) las carga solas cuando se usan, traduciendo el namespace App\ a la carpeta app/.

PDO y las consultas preparadas

PDO es la forma de hablar con MySQL desde PHP. "Preparada" significa que el SQL y los valores van por separado: primero se manda la consulta con marcadores (:id), después los valores. Así un valor nunca puede cambiar la consulta. Es la regla 1 de seguridad.

password_hash() y password_verify()

La contraseña nunca se guarda en texto: se guarda su hash (una huella irreversible) con password_hash(). Al iniciar sesión, password_verify() compara lo que escribiste contra esa huella. La respuesta de seguridad se guarda igual.

Sesiones: session_start(), $_SESSION, session_regenerate_id()

La sesión recuerda quién sos entre páginas. El front controller hace session_start(); al entrar bien, se guarda $_SESSION['usuario_id'], el nombre (para el saludo) y el rol (para el guardia de admin). session_regenerate_id() cambia el id al iniciar sesión, para evitar el robo de sesión.

6. Las 5 invariantes y dónde se cumplen

Las cinco reglas que el proyecto no rompe nunca, cada una con el archivo y el bloque que la implementa.

  1. Sin inyección SQL: todas las consultas usan prepared statements en los modelos (app/Models/).
  2. Control de sesión: el guardia Auth protege las rutas privadas; el login guarda el usuario en la sesión.
  3. Sin XSS: todo lo que se muestra pasa por e() en las vistas.
  4. Roles: el guardia Admin cierra la sección Usuarios a quien no sea admin; hay candados para no quedar sin administrador.
  5. Sin JavaScript: los gráficos del tablero son CSS puro; toda la lógica corre en el servidor.

7. Límites conocidos

Lo que este proyecto no resuelve, dicho de frente. Es un trabajo educativo: señalar un límite y explicar por qué está ahí enseña más que disimularlo.

  • No hay tokens CSRF en los formularios: queda fuera del alcance de este trabajo educativo.
  • La recuperación de contraseña es por pregunta de seguridad, no por correo.
  • Los roles son dos y fijos (admin / usuario); no hay permisos finos.
  • Las URLs limpias (sin index.php/) dependen de cómo se sirva el sitio; por eso se usa el patrón con index.php/, que funciona en cualquier lado.

8. Dónde está cada cosa

La estructura de carpetas y el criterio detrás de ella.

La idea es que un recién llegado distinga de un vistazo qué es cada cosa:

  • public/ — la cara visible: lo único que el navegador abre directo.
  • app/ — el servidor (backend): el código PHP, con el MVC adentro.
  • database/ — la base de datos (tablas, migraciones, datos de prueba).
  • docs/ — las guías.

El criterio clave: el código sensible (app/, config/, secrets.php) vive fuera de public/, así el navegador físicamente no lo alcanza — no por una regla que lo prohíbe, sino porque no está en la carpeta servida.

Esquema de la base de datos (diagrama)

Las tres tablas, sus atributos y cómo se relacionan. PK = Primary Key (clave primaria, el identificador único de cada fila).

Entidades, atributos y relaciones

  • productos: id (PK), nombre, descripcion, precio, stock, categoria, fecha_creacion.
  • categorias: id (PK), nombre (UNIQUE, no se repite), fecha_creacion.
  • usuarios: id (PK), usuario (UNIQUE), nombre, apellido, rol (admin/usuario), password_hash, pregunta, respuesta_hash, fecha_creacion.

Relación: productos.categoria es una clave foránea (foreign key) hacia categorias.nombre: cada producto puede pertenecer a una categoría de la tabla, o a ninguna (valor NULL). Por eso DBeaver y phpMyAdmin dibujan la línea de relación entre las dos tablas. La regla es ON UPDATE CASCADE (si se renombra la categoría, los productos la siguen) y ON DELETE SET NULL (si se borra, sus productos quedan sin categoría). usuarios es independiente de las otras dos.
